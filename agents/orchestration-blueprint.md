# 🧭 오케스트레이션 청사진 (Orchestration Blueprint)

> 수석 비서 에이전트가 강의 지식을 뇌로 삼아 작업을 분배·통합하는 설계도.
> 강의의 **황금 3법칙**과 **RAG 3단계 도식**을 운영 원리로 그대로 채택한다.

---

## 1. 역할 정의

**오케스트레이터(Orchestrator)** = 지시를 해석하고, 작업을 쪼개 적절한 실행 주체에 배분하고,
결과를 통합·검증하는 지휘자.

- 단순 Q&A가 아니라, **찾은 정보로 다음 단계까지 자율 실행**(법칙3: 에이전트화).

---

## 2. 작동 구조 (RAG 3단계 매핑)

```
[사용자 지시]
     │
     ▼
┌──────────────────────────────────────┐
│   수석 비서 에이전트 (오케스트레이터)    │
│   1. 지시 해석          (Query Encoder)│
│   2. 지식 검색          (Retriever)    │ ◄── claudeWIKI = 논파라메트릭 메모리
│   3. 작업 분배 & 결과 통합 (Generator)  │
└──────────────────────────────────────┘
     │            │            │
     ▼            ▼            ▼
 [서브에이전트]  [서브에이전트]  [서브에이전트]   ← 손발 (병렬 실행 가능)
   코드 작성      문서 정리      검증/리뷰
```

| RAG 단계 | 오케스트레이터의 행동 |
| --- | --- |
| Query Encoder | 사용자 지시의 의도·범위 파악 |
| Retriever (MIPS) | 이 저장소에서 관련 지식 문서 검색·참조 |
| Generator | 작업을 서브에이전트에 분배하고 결과를 논리적으로 통합(Marginalize) |
| Backprop | 결과 검증 → 틀리면 원인 추적해 재시도 |

---

## 3. 운영 원칙 (황금 3법칙 적용)

1. **지식 구조화가 먼저**
   - 모든 학습/작업 산출물은 이 저장소의 정해진 구조(`lectures`, `concepts`, `practice`, `agents`)에 축적.
   - 연관 문서끼리 상호 링크하여 '지식 네트워크'를 형성.
2. **목적에 맞는 모델/도구 선택**
   - 탐색·검색이 많으면 Explore 류, 설계는 Plan 류, 광범위 다중작업은 일반 에이전트.
3. **에이전트화**
   - 받은 지시를 끝까지 실행(작성 → 커밋 → 푸시)하고, 막히면 명확히 질문.

---

## 4. 영속성 규칙 (Ephemeral 대응)

- 세션은 임시이므로, **모든 학습/결정은 커밋·푸시로 영속화**한다.
- 다음 세션의 에이전트는 이 저장소를 **논파라메트릭 메모리로 다시 로드**하여 이어서 작업한다.
- `README.md`의 "학습 진행 현황"을 항상 최신으로 유지 → 새 세션의 진입점.

---

## 5. 표준 작업 흐름 (강의 1회분이 들어올 때)

1. **수신:** 사용자가 강의 스크립트/교재 제공.
2. **구조화:** 핵심을 `lectures/weekN/dayN-주제.md`로 정리, 새 개념은 `concepts/`에 추가.
3. **연결:** 관련 문서 상호 링크, `README` 진행 현황·인덱스 갱신.
4. **실습 반영:** `practice/`에 실습 항목·상태 기록.
5. **영속화:** 커밋 + 푸시.
6. **요약 보고:** 무엇을 배웠고 무엇이 남았는지 사용자에게 보고.

---

## 6. 향후 확장 (Step 2: Agent 단계 대비)

- 5~8주차에서 자율 에이전트를 다루게 되면, 이 청사진에 **구체적 워크플로우**
  (수익 창출 파이프라인, 트리거 → 액션 정의 등)를 `agents/` 하위에 추가한다.
- Graph RAG / Agentic RAG 학습 시 검색 구조 고도화 내용을 반영한다.
